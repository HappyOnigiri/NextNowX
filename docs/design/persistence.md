# 永続化と設定の方針

Next Now X は SQLite を使い、インストール・調査・バックアップをローカルで完結させる。
この設計は、ローカルのデータベースを 1 つにまとめる代わりに single-writer の制約を受け入れる。
正規化されたスキーマにより、将来 PostgreSQL へ移行する余地を残す。

CLI とサーバの設定は 1 つの設定ファイルを共有する。
CLI の振る舞いに影響する設定はこのファイルに保存し、WebUI の表示だけに影響する設定はブラウザの Local Storage に保存する。
表示言語は CLI が描くプロンプトの言語でもあるので、この共有設定の `language` キーに保存する。値は `auto`・`en`・`ja` のいずれかで、キーがなければ `auto` として扱い、`auto` はファイルに書き出さない。実効言語の決め方は [agent-prompts.md](agent-prompts.md) にある。

永続的な変更と migration はアトミックである。
設定の書き込みは、ローカルの秘密ファイルの保護を保ったままアトミックな置換で行う。

記録された migration のバージョンと実際のスキーマが食い違う場合は、スキーマを正とする。
データベースを開くときは、何かを適用する前に記録を修復する。スキーマが存在しないバージョンは記録を失い、スキーマがすでに適用されているバージョンは記録を取り戻す。
これにより、自分が知る形でしかスキーマを認識しない古いビルドが、後の migration で作り替えられた記録を削除した後でも、データベースを開けるままにできる。
すでに先へ進んだスキーマに対して migration を再適用することはない。

サポートされたバージョンの設定ファイルは、未知のフィールドを含んでいても読み込める。
そうしたフィールドはコマンドやサーバ起動を失敗させず警告として報告し、次に設定を書き込むときに削除する。
サポート外のバージョンとその他すべてのデコード失敗では設定を読み込まない。壊れた、あるいは曖昧なファイルを黙って受け入れることはない。

稼働中サーバの記録は設定ディレクトリ配下の `nnx/run/serve.json` に置き、寿命はそのサーバプロセスと同じである。
このファイルは多重起動防止の flock を兼ねるので、書き換えは設定ファイルと違い rename ではなく in-place で行う。rename は inode を差し替えて保持中のロックを無効にしてしまう。
正常終了時は内容を空にするだけで、ファイルは残す。詳細は [daemon.md](daemon.md) にある。

ローカルデータベースの変更は、`PRAGMA data_version` を専用の接続 1 本から周期的に読んで検知する。
この値は接続ローカルで、その接続以外がコミットすると変化する。別プロセスである CLI の書き込みも、同じサーバプロセス内の別接続による書き込みも同じように現れる。
プールから都度借りて読むと接続ごとに違う値を返すので、検知の手段として成立しない。専用の接続をサーバ全体で 1 本だけ持ち、`PRAGMA data_version` 以外には使わない。他のクエリを走らせたり結果セットを開いたまま残したりすると読み取りトランザクションが張られ、値が凍結して無言で検知が止まる。
値そのものは外へ出さない。内容とも時刻とも無関係で、プロセスをまたいで意味を持たないためである。外へ出すのはサーバプロセス内で 1 から単調増加するリビジョンで、再起動で 1 に戻る。
値は 32 ビットで折り返すので、比較は大小ではなく異同で行う。
接続の上限が 1 本の構成（`:memory:`）では専用の接続を取らず、変更検知を利用不可として扱う。専用の接続を握った時点で他のすべてのクエリがプール待ちで止まるためである。
既知の限界として、データベースファイルを丸ごと差し替える操作は検知できない。バックアップからの復元や `mv`・`cp` による置換では inode が変わり、サーバの接続は古い inode を見続けるので値が永久に不変になる。
CLI とサーバが別のデータベースを開いている場合は、変更が届かないのではなく「何も起きていない」ように見える。どちらがどこを開いているかは `nnx debug` が報告するパスで切り分ける。

テンプレートと同期の設定に関する方針は、[agent-prompts.md](agent-prompts.md) と [github-sync.md](github-sync.md) にある。

task ラベルの global 設定と scope ごとの保存形式は [task-labels.md](task-labels.md) に記録する。

`nnx serve --demo` は、サーバプロセスごとに新しい一時データベース・設定・Markdown document 一式を作る。
通常のデータベースと設定のパスは、環境変数で指定されたものも含めて読み書きしない。
一時環境は正常終了後に削除し、異常終了した場合も再利用しない。
demo でのすべての変更操作はそのプロセスが終了するまで利用できるので、WebUI は通常のアプリケーションと同じように振る舞う。
demo は稼働中サーバの記録を書かず、flock も取らない。一時データベースを毎回作るので、複数の demo を同時に動かしてよい。

## 初回のサンプルデータ

`nnx setup` は、起動時にデータベースファイルを新規作成したときだけ、小さなサンプル（project 1・feature 1・task 6・document 2）を通常のデータベースへ投入する。
インストール直後のデータベースは空なので、task・依存・表示状態という中心概念を、利用者が自分でデータを作るまで一度も見られない。それを初回の 1 画面で見せるためである。
投入するのは `nnx setup` だけである。`nnx serve` を含む他のコマンドは、データベースを新規作成しても投入しない。

投入済みかどうかを覚える設定値は持たない。判定はデータベースファイルの有無だけで、`nnx setup` がファイルを作った実行だけが投入する。
そのため、サンプルを削除した後で `nnx setup` を実行しても投入は起きず、データベースファイルを消せばまた投入される。
`:memory:` と `file:` DSN は投入の対象外である。ファイルを持たないデータベースは初回のインストールを表さない。
既存の 0 バイトのファイルも新規作成ではないものとして扱う。
stat と `sql.Open` の間に他のプロセスが同じデータベースを作る競合窓は残るが、経路が `nnx setup` だけで、その時点では常駐サーバも動いていないので許容する。

opt-out の手段は 2 つある。`nnx setup --no-sample-data` と環境変数 `NNX_NO_SAMPLE_DATA` である。
環境変数は空でない値をすべて opt-out として扱う。真偽の語彙を決めると、インストーラが `false` を渡したときに投入してしまう。
opt-out のときはデータベースを開かない。

文言は実効言語（en / ja）で出し分ける。実効言語の決め方は [agent-prompts.md](agent-prompts.md) にある。
その実行の実効言語は `nnx setup` が最初に尋ねる言語の選択で決まる（[daemon.md](daemon.md)）。投入は文言を DB へ書くので、後から `language` を変えても入れ直しは起きない。
投入したときだけ標準出力へ実効言語で 1 行を出す。詳細は [cli-contract.md](cli-contract.md) にある。

サンプルに pull request は含めない。pull request を紐づけると直後に同期が走るので（[github-sync.md](github-sync.md)）、実在しないリポジトリの同期エラーと stale が初回から残る。
document は URL でもローカルファイルでもなくインラインの Markdown にする。どちらも環境によって開けなくなる。

投入の失敗は `nnx setup` を失敗させない。`install.sh` は `nnx setup` の終了コードだけで TUI が使えたかを判断するので、投入の失敗で常駐の案内が消えるのは割に合わない。
データベースを開けない場合も書き込みに失敗した場合も、警告 1 行を stderr に出して常駐の問いかけへ進む。
書き込みが途中で失敗したときは、作った project を cascade 削除して巻き戻す。中途半端なグラフを初回の画面に残さないためである。巻き戻しにも失敗した場合はそれ以上追わない。

これは `nnx serve --demo` とは別物である。demo は一時データベースへ大きなショーケースを毎回作り、通常のデータベースには触れない。

## Document と implementation plan

snapshot 中の document の項目は、派生状態に必要なメタデータだけを持つ。

document は project・feature・task いずれの参照にも同じモデルを使い、各 document はそのうちちょうど 1 つに属する。
各 document が持つ source はちょうど 1 つで、HTTP または HTTPS の URL、登録済みのローカルファイルパス、インラインの Markdown のいずれかである。
インラインの Markdown は 1 MiB までで、詳細読み取りのときにだけ読み込む。

task は最大 1 つの document を implementation plan に指定できる。
この指定は task だけのものである。project や feature の document が plan になることはない。
この指定により、pull request のない未着手または designing の task は designed の表示状態に移る。readiness、依存の充足、完了状態は変わらない。
plan 以外の document、feature の document、project の document には、アプリケーション層での件数制限はない。
