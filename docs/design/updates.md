# 更新の確認と適用の方針

利用者が GitHub Releases を見に行かなくても、新しいリリースが出たことに気づけるようにする。
気づいた場所でそのまま更新できることまでを機能の範囲とし、利用者の操作なしに更新することはしない。

## 配布元は固定で、確認は未認証で行う

確認先は Next Now X 自身の配布元である `HappyOnigiri/NextNowX` の Releases だけで、設定で変えられない。
利用者が同期しているリポジトリとは無関係なので、`internal/github` が解決する資格情報は使わず、未認証の Releases API を読む。
配布元へ利用者のトークンを送る理由がない。

未認証の API は IP あたり毎時 60 リクエストに制限される。
呼び出し上限に達した失敗は、権限やネットワークの失敗と区別してメッセージにする。次に取るべき行動が「待つ」である点だけが違うためである。

案内の対象は、draft と prerelease を除いた、現在のバージョンより新しいタグである。
新旧の判定は semver の比較で行い、文字列の不一致では判定しない。保持する件数には上限を設ける。

## 有効なのはリリースビルドの非 demo だけである

開発ビルド（`-dev`）は配布物そのものではなく、置き換える対象も配布物ではない。
`nnx serve --demo` は一時的な設定と一時的な DB で動く隔離実行で、実ネットワークに出てはならない。
どちらの場合も確認も適用も行わず、無効であることと理由を構造化して返す。案内も出さない。
これに加えて、更新機能をビルドから外したときも同じ枠組みで無効を表明する。

## 更新機能はビルド時に外せる

`noupdate` ビルドタグを立てたビルドでは、更新機能をコンパイル対象から外す。
配布元の URL を持つ実装ごと外すので、タグ付きのバイナリには配布元の文字列が残らない。
真偽値を ldflags で埋める方式は、URL の定数がコンパイルされ続けるのでこの目的を満たさない。

外すのは配布元を読む実装、インストーラーを取得して実行する実装、`nnx update` コマンド、およびそれらの配線である。
タグ付きのビルドでは `update` サブコマンドが登録されず、無効の理由として `excluded_from_build` を返す。
WebUI は案内すべきときだけ案内を出すので、無効を返すだけで案内もモーダルも出なくなる。

無効の判定はバージョンの値より先に効く。
更新機能を持たないビルドは任意のバージョン文字列を名乗ってよく、`-dev` 接尾辞も semver の形も、そのビルドでは意味を持たない。

タグを立てない既定のビルドの挙動は、この仕組みを入れる前と同一である。
タグ付きのビルドが腐らないよう、ビルド・テスト・配布元の文字列が残らないことを CI で検査する。

## 状態は意思表明と機械の記録に分ける

「このバージョンをスキップ」は利用者の意思表明である。ブラウザを変えても残るべきなので `config.yaml` の `update.skipped_version` に置く。
スキップは「そのバージョン以下を案内しない」という意味であり、より新しいタグが出れば案内は自動的に戻る。指定を期限で消したりはしない。

「最後に確認した時刻」と「確認結果のキャッシュ」は機械内部の状態なので SQLite の singleton テーブルに置く。
キャッシュを持つのは、モーダルを開くたびに配布元を叩かないためと、オフラインでも直近の内容を表示できるようにするためである。

自動確認は GitHub 同期と同じく日和見的に駆動し、バックグラウンドワーカーは増やさない。
間引きの判定と実行権の付与は 1 つの条件付き UPDATE で行い、同時に来た複数のタブや CLI のうち 1 つだけが確認に出るようにする。間引きは 24 時間に 1 回である。

確認の失敗は記録して次回に回し、画面の読み込みやコマンドを失敗させない。
例外は `nnx update` が明示的に依頼した確認で、これは失敗させる。利用者が今その結果を求めているためである。

## 更新の実行は Release 添付の `install.sh` に委ねる

`docs/development.md` の「更新は初回導入と同じコマンドで行う」をそのまま守る。
checksum 検証・版番号検証・atomic な置換・PATH の案内はすべてインストーラーが持つので、Go 側に二重実装を持たない。
`nnx` は対象リリースの `install.sh` を取得して `bash` で実行するだけである。

取得元は `latest/download` ではなく確認したタグを指す。確認した版と実際に入る版を一致させるためである。
タグは semver として読めた値だけを受け付ける。取得元の URL に任意の文字列を差し込ませないための検査でもある。

実行は非対話で行う。標準入力は渡さず、実行の上限時間を必ず設ける。
インストーラーは `~/.local/bin/nnx` も改名前の `~/.local/bin/prx` も存在しないときだけ `nnx setup` の TUI を起動するので、通常の更新経路では起動しないが、応答が返らない状態を構造的に避ける。
起動は新しいセッションで行い、制御端末も渡さない。標準入力を閉じるだけでは `nnx setup` が `/dev/tty` を開けてしまい、誰も答えない問いかけを上限時間まで待つ。

環境は `PATH` と `HOME` を明示して渡す。
launchd が常駐へ渡す環境は極小なので、これを書かないと常駐からの更新だけが失敗するサイレントな差分になる。`docs/design/daemon.md` が `EnvironmentVariables` で対処しているのと同じ問題である。
これに加えて、プロキシと CA の指定だけを許可リストで引き継ぐ。インストーラーの中の `curl` が外へ出られないと、Go 側の取得が通るのにスクリプトの取得だけが落ちる。

インストーラーは配置先を固定しているので、`make install` で `INSTALL_DIR` を変えた配置や別の場所にあるバイナリは更新されない。
置き換えが起きたかどうかはインストーラー自身の報告で確かめ、報告がなければ失敗として扱う。何も置き換えずに成功と伝えてはならない。

## 改名前の prx からの更新

改名前の `prx` は `HappyOnigiri/PRX` の Releases を読み、そのタグの `install.sh` を実行する。
GitHub はリポジトリの改名後も旧名の API とダウンロードを新しい名前へ転送するので、旧バイナリも新しいリリースの `install.sh` を取得できる。
旧バイナリは `Installed prx <version> to <path>` の行で置き換えを確かめるので、`install.sh` は `~/.local/bin/prx` か `com.user.prx` の plist を見つけたときだけこの行も出す。

`install.sh` はそのうえで、旧 plist があれば `nnx daemon install` で LaunchAgent を移し、`~/.local/bin/prx` を削除する。旧バイナリがあれば初回の導入とは扱わず、`nnx setup` は起動しない。
旧常駐から実行された更新では、LaunchAgent の移行が呼び出し元の常駐を止め、出力のパイプも閉じる。移行を出力から切り離した子プロセスで行うので、呼び出し元と一緒には止まらない。
そのため旧常駐の WebUI からの更新は、応答を返す前に接続が切れて失敗と表示されることがある。新しい常駐は移した設定のアドレスで起動する。

## 常駐の再起動には介入しない

`docs/design/daemon.md` のとおり、launchd 配下の常駐はバイナリ置換を自分で検知して再起動する。
更新の経路はここへ介入せず、kickstart もしない。管理外のプロセスが自己 kickstart すると、置換側がロックを取れずに終了する。

常駐外で動いている `nnx serve` は古いまま動き続けるので、再起動が必要である旨を結果に含めて返す。
サーバーが稼働していない環境に再起動を促す意味はないので、そのときは何も伝えない。

## 操作面

WebUI はサイドバーの足元に、案内すべきときだけ案内を出す。
モーダルは現在のバージョンから最新までの各リリースの本文を Markdown で表示し、「今すぐ更新」「このバージョンをスキップ」「キャンセル」を選べる。
更新中はモーダルを閉じさせず、Escape も背後へ渡さない。

CLI の `nnx update` は確認だけを行い、`nnx update --apply` は更新も実行する。
端末があり `--json` でも `--apply` でもないときは、確認結果を表示してから更新するかを尋ねる。キャンセルは成功として終わる。
CLI は案内を出さないので、スキップの設定を読まない。
確認だけなら開発ビルドでも状態として成功するが、`--apply` は実行の依頼なので終了ステータスでも失敗させる。
